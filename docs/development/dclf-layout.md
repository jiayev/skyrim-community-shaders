# DCLF code layout

This is how Drawcall Limit Fix's code is laid out, the extension points its features build on, and the rules
`tools/dclf-layout-check.py` enforces. How DCLF works, and why, is [dclf-architecture.md](./dclf-architecture.md). The
switches, parity checks and run procedure are [dclf-validation.md](./dclf-validation.md). Work not built yet is
[dclf-roadmap.md](./dclf-roadmap.md).

## The target

The tree as it is. Rule 5 keeps its top level and `Core/`'s subfolders closed (`TOP_LEVEL`, `CORE_SUBFOLDERS` in the check).

```
src/Features/DrawcallLimitFix.{h,cpp}   the shell: CS's one integration point (Feature overrides, hook thunks, menu)
src/Features/DrawcallLimitFix/
  Api/            the extension API: the contracts features and integrations build on (standard and ORG types only)
  Core/           what every feature builds on, with no feature knowledge
    Runtime/        the building blocks (KeptState, SlotTable, EventQueue, Retirement, LatestSlot, ...) and the scene
                    executor, graph and scheduler
    Engine/         engine access, the read window, the releases, the render-thread budget, shell state, the frame clock,
                    skin palettes and partitions, walkers
      Capture/        the engine's writers hooked, record reads, the event channels (SceneCapture, SceneEvents, SceneTracker,
                      ConstantMirror)
    Settings/       the switches and toggles
    Scene/          the scene: the channels, the entry space, the pump's wake
      Coordinator/    the coordinator's core: tracked entries, slots, walk, set and claims, pump (State/: its components)
      FrameView/      the render thread's half of the scene
      Model/          records, tables, publication, the mirror, eligibility, lookups
    Handoff/        taking objects from the engine: primary cull, scene lists, pass capture, shadow views
    Shading/        the material port framework (Lighting's and the geometry port), material sources and writes, constants,
                    lighting descriptors, frame globals, vertex input
    Gpu/            frame values, frame data, pooled backings, the build executor, GPU resources and textures,
                    Pipelines/ (one file per family), PlacementRows/
    Render/         IndirectDraws (IndirectDraws.h; its implementation: Impl.h, Impl/, Internal.h), the frame driver,
                    Snapshot/, Revision/, Payload/, Epochs/ (the epoch framework and the schedule's executor), Passes/,
                    Main/, Views/, Shadow/ (the shadow engine), DrawFamilies/, Readback/, Resources/
    Extensions/     the extension registry (Registry) and the Core halves of Api/'s contracts
  Features/       one folder per engine feature DCLF ports (MainView, Forward, FirstPerson, Reflection, OcclusionMaps,
                  Shadows/{Engine,Sun,Local}, Portals, GpuOcclusion, LocalLights, Skins, Actors, Faces, Particles, Billboards,
                  Decals, Effects, Landscape, Fades, Lod, TreeLod, TreeWind, TextureTransforms, HiddenNodes, SwitchNodes),
                  each with its own Diagnostics/ where it has parity checks; FeatureList.cpp (the install order) and
                  Manifest.cpp (the shared shader constants' overlap check)
  Integrations/   one folder per CS feature DCLF supports, written against Api/ (AdvancedSkin, TerrainBlending,
                  LightLimitFix, TruePBR, SubsurfaceScattering, ExtendedTranslucency, LinearLighting, VolumetricShadows,
                  CloudShadows, ExponentialHeightFog, DynamicCubemaps, Skylighting, TerrainShadows, WaterEffects, IBL);
                  IntegrationList.cpp
  Diagnostics/    the observer infrastructure (Hooks.h, Observation, Policy, Install), the parity checks that span
                  features (Scene/, Engine/, Draws/), the feature-level probes (Feature/), the periodic report (Reports/),
                  the schedule dump and the test harness
  Schedule/       the frame's schedule: its triggers, every epoch and its passes' keys in order (Frame.cpp), which only
                  the shell includes
```

A feature's shaders are under `features/Drawcall Limit Fix/Shaders/DrawcallLimitFix/Features/<X>/` (Fades, GpuOcclusion,
TextureTransforms, TreeLod, TreeWind); Core's (BuildDrawsCS, VisibilityEventsCS, the sorts, the index pool, the foliage parity)
are beside that folder.


The main view's own work is a feature, `Features/MainView`: its draw passes (`MainOpaquePass`: `main-view.z.depth`,
`main-view.depth-phase2`, `main-view.colour`) and the main pass's capture and colour epoch, which `FrameDriver` calls at the main
pass's points through the primary view contract (`Api/PrimaryView.h`). Core keeps what every view shares and every contract hangs
off: the frame commits (the depth commit, the colour commit and its frame constant slots, `IndirectDraws::ExecuteColour`), the
BuildDraws passes of both main phases and phase 2, the latched copies, the index pool, the sorts, visibility and its readback, the
frame constants, the z-bucket counts, the native targets and depth (first person draws into them), the shapes, the revisions and the
view engine (`Core/Render/{Main,Epochs/MainEpochs.cpp,Passes/CorePasses.cpp,Passes/MainExtension.cpp}`).

The shadow engine's epoch half is a feature too, `Features/Shadows/Engine` ("shadow-epochs", namespace
`DCLF::Features::Shadows::Engine`): the shadow and occlusion epochs' passes (`ShadowBuildDrawsPass`, `ShadowViewPass`, in
`namespace DCLF::Draws`; the latched copies; the index pool's copies and the culling counters' readback through Core's factories:
`shadows.*`, `shadows.sky.*`) and their frame points, which `FrameDriver` calls at the engine's shadow and occlusion points through the
shadow epochs contract (`Api/ShadowEpochs.h`): the views' coverage and the shadow frame begun, the shadow epoch, the occlusion maps'
readiness and their epoch. Shadows/Sun, Shadows/Local and OcclusionMaps build on it (DEPENDS). Core keeps the scene side (see
"Remaining architectural flaws").

`Features/`, `Integrations/` and `Diagnostics/` are areas, not layers: one folder per feature or integration, and the checks.
`Diagnostics/{Scene,Engine,Draws}` keep layer names (see "Not yet in place").

A feature's folder owns everything about that feature:
- its engine hooks;
- its coordinator state;
- its table columns and records;
- its frame-value pool;
- its passes (and its shaders, in the shader tree's `Features/<X>/`);
- its toggles;
- its parity checks and report lines.

Features register at install, before DCLF's threads start. Their callbacks run per phase or per chunk, never per object (the exceptions
run per event or per walked entry, where Core already classifies: a material port's callbacks, an occlusion map's occluder rule).
The bits that shaders share stay compile-time ("The extension points").

## The extension points

A feature is an `Api::Feature`: a name and an install function. It is listed in `Features/FeatureList.cpp`, the one place
that shows what DCLF does. The shell's `PostPostLoad` calls `Extensions::InstallFeatures` before DCLF's threads start.
Install registers the feature's parts through `Api::InstallContext`. The registry (`Core/Extensions/Registry`) is
read-only after that. A feature may also name early hooks (`Api::Feature::earlyHooks`): engine hooks Core's engine side must
find in place when it installs (a vtable slot the primary cull takes, a call site the primary cull requires: Features/Portals' walk,
noted with `Extensions::NoteMainWalkInstalled`; the source of an engine event channel Core follows, or a writer completing Core's movers
on a move-writer slot it reserves first), which
the shell runs after Core's scene events and before DCLF's own engine hooks and observers (`Extensions::InstallEarlyHooks`). And it
may name source hooks (`Api::Feature::sourceHooks(Api::ShadowSourceHooks&)`): a shadow source's engine hooks, its culls' (which call
`ShadowSourceHooks::CullsInstalled` once they are in, read as `Extensions::SourceCullsInstalled(source)`) and those that write its cameras
into its own boards (with Core's camera math, `Core/Render/Shadow/ShadowCameras.h`; Core reads them through the source's `camera` and the
sun volume), which the shell runs where the shadow sources' hooks install
(`Extensions::InstallSourceHooks`, before the primary cull). They are called once per source, with the source, in `Api::ShadowSource`
order (at each source the features in the list's order): Features/LocalLights' light selection installs at the Spot source, Features/Shadows/Local's
point culls at the Point source, so the hooks' install order, and the install log's, is the sources' (the sun's accumulation and
UpdateCamera, the light selection, the point lights' culls, the focus cameras), whatever the features' places in the list.

An integration (a CS feature DCLF supports) is an `Api::Feature` too, listed in `Integrations/IntegrationList.cpp` (`Integrations::List`,
ordered as `Features/FeatureList.cpp` is) and installed by `Extensions::InstallFeatures(features, integrations)` after every feature and
before the resolutions, so what it registers may name what a feature registered (Integrations/AdvancedSkin's wetness: Features/Actors'
published actor-owned class). It has no early or source hooks (the install fails otherwise). Its parities are in
`Integrations/<X>/Diagnostics/`, called from the Diagnostics observers that report them (CaptureParity's skin line, SceneFrameLines'
shading line), their text unchanged.

defines them in companions under `Core/Extensions/` (`FrameValuePools.h`, `PassContext.h`, `PayloadProducts.h`,
`SceneResources.h`, `Commits.h`, `FrameBindings.h`, `Reports.h`, `EngineEvents.h`, `TableFamilies.h`,

`VertexStreams.h`, `PaletteRows.h`, `MaterialPorts.h`, `Materials.h`, `ProgramFamilies.h`, `MaterialWrites.h`, `NodeCaptures.h`, `ShadingFields.h`, `ClassifyInputs.h`, `LightVolumes.h`, `SunVolume.h`, `AncestorValues.h`, `DepthPyramid.h`; the shadow exclusion's build
is `Core/Render/Shadow/ShadowExclusionBuild.h`), which features
inside DCLF include for typed access to Core's types.

Residency changes are events, so a coordinator component's hooks are function pointers called per changed slot. The loops
that run every frame over every object (the walk's evaluate, the builds' packing, the commit) never call a feature: they read
what it registered as data (a technique's flags and toggle, a geometry type's or a parent's toggle, a family's references and record
word). The switches and toggles register with `Core/Settings`, which owns them.

The shaders' shared constants stay compile-time: a feature declares its own (a frame binding's register beside its HLSL
declaration, its object flag bits within `kFeatureObjectFlags`, its family's record word), and `Features/Manifest.cpp`
checks them against Core's and each other's.

Not generalised (each a deliberate Core part, not a contribution):
- **Billboard placement row** (`Core/Gpu/PlacementRows/BillboardRow`: `PlacementRows::SampleBillboardRow`, `BillboardFaceMode`). An item has
  one class (a particle under an NiBillboardNode gets both treatments; a class would change its rows and make them due every frame); three

  layout is the frozen decode of Effect.hlsl's `DCLFBillboardWorld`. A static call. Features/Billboards keeps the switches, toggle, parent
  contributions, the CPU turn and its parity.
- **Shadow texture-transform scroll** (`Extensions::DrainTransformMoves`, `Core/Extensions/MaterialWrites.h`; ShadowBuild's `ShadowTexcoord`
  and `WatchTransformMoves`), and not Features/TextureTransforms'. The shadow material rows read the transform on the CPU in every
  configuration; TextureTransforms has no switch, and depending on it would need a banned fallback; a GPU patch would add a shadow pass and
  a material map; a ShadowViews row contribution would be a per-object-per-frame callback; and `ShadowMaterialRow` is Utility.hlsl's frozen
  layout. The hooks push every move to the `TransformMoves` queue (the Lighting float controller's, in `Core/Shading/MaterialWrites.cpp`)

## The view contract

The engine views Core's bucketed view machinery draws (`ViewTraits`, `ViewFrame`, `ViewResources`, `ViewLatchLayout`, `PlanViewBuckets`,
`MakeViewShape`, `CommitView`, `ViewExtension`) are taken by features through one contract: `Api/Views.h` (`RegisterView`,
`RegisterViewWork`), with its Core companion `Core/Extensions/Views.h`. The reflection's faces and the first person are on it. The
occlusion maps and the shadow views are another family (`ShadowFrame`), on the sibling contract below; what both families share is
`Api/ViewCommon.h` (`ViewPoint`, a feature view's `ViewBits`) and its companion `Core/Extensions/ViewCommon.h`. The portals (the main
cull input, `Api/CullInputs.h`), local lights, GPU occlusion (the depth pyramid, `Api/DepthPyramid.h`) and the forward epoch (two object
classes and the engine's forward points) are not views.

- **Core's fixed slot per view.** `Api::EngineView` is Core's slot order (`Reflection`, `FirstPerson`): the epochs' indices, the latches,
  the revision key groups, the coverage and the setup run in it. `Core/Render/Views/ViewSlots.h`'s `kViewSlots[v]` reserves the view's
  epochs (`Epoch::*`, whose `kEpochTraits` order is load-bearing), its `RenderGraphRuntime::Segment`s, its key group (the shapes-made
  report's names, "reflection" and "first person") and its graph extension's id. A new view is the enum value, a CS segment, its slot
  row, then the feature's registration.
- **The feature supplies data and per-frame callbacks.** `ViewContribution`: the view, its toggle, its set phase (one bit, the feature's)
  and its shape's view bit (one bit, the feature's: both checked against Core's and each other's by the install and by
  `Features/Manifest.cpp`), its membership (`CategoryRoot`: the entries under the root `captureRoot` names, an exclusive phase whose main
  mask is the view bit alone; `LodTechniques`: a main-eligible slot whose pipeline is a LOD Lighting technique, beside the main phase),
  its key rule (`lodTechniquesOnly`, `forwardRasterToForwardPart`; `keyFlags`, the view's own forward key bits, above Core's two-sided and
  tree LOD bits, at most one view without any, by which the pipeline lane finds a key's view, `Extensions::ForwardKeyView`,
  `ViewSet::plainKeyView`, `ResolveViews` failing overlapping bits or a second view without any; `cullBackFaces`: back faces unless
  two-sided, else front faces, a cube face's mirrored projection), its shape (`faces` up to `kMaxViewFaces`, `trees`,
  `forwardPart`, `depthPass`, `viewBits`, names and latch labels, the initial `depthRange`), its life (`KeepLast`, `DropWhenOff`: dropped
  from the revision while off), its area (`Target`, `MainColourViewport`), its withholding (`InMainRenderers` with the `accumulators`
  callback; `OwnRenderers`, whose renderers its engine hooks name), its target import (`ColourWithOwnDepth`, `DepthTarget`), its coverage
  before the first decision and on a failed graph, its decals as forward objects, and its `covered` callback (required; render thread,
  once a frame at `DecideCoverage`, the views in slot order, over Core's precomputed, side-effect-free `ViewCoverage`), and an OwnRenderers
  view's optional `residueDue` (render thread, once per render that would leave the view's LOD roots to DCLF,
  `IndirectDraws::ViewLodRootsOwned`: whether that render keeps them, the view's renderers' unwithheld passes under them watched,
  `PassCapture::WatchViewResidue`, `TakeViewResidue`, `TakeViewResidueGeometries`; the install refuses it on another view). `ViewWork` runs
  the feature's work at a `ViewPoint` (`FrameStartBeforeCoverage`, `FrameStartAfterTreeLod`, `DepthCommitted`), once a frame on the render
  thread, the views in slot order and a view's work in registration order, whatever the toggle (the work reads it).
- **Resolved once, read as data.** `Extensions::ResolveViews` (the end of `InstallFeatures`) makes each view's `ViewEntry` (none for a view
  no feature takes: every per-view loop skips it) and derives what the per-object paths read: the set's phases, `rootPhases` and
  `lodPhases`, the view bits, the root views, the set decision's order (the CategoryRoot views first),
  and the InMainRenderers and OwnRenderers views. Classification, the set decisions (`SetParticipation`, `DecideSlot`, the slot
  readiness by membership: `IndirectDraws::ViewSlotReady`, a LodTechniques view's phase readiness: `PhaseReady`), the lacking phases
  (`lodPhases`: FrameView's third count), the builds' masks, the frame requests' roots, the revisions (traits, forward keys, key groups,
  `DropWhenOff`) and `PassCapture` read the entries; no per-object loop calls a feature. Then `Extensions::ResolveViewBits` checks
  both families' phases and view bits (one bit each, none Core's nor another view's) and makes `ViewBitsOf`'s table by phase mask and
  the lacking counts' phases (`Extensions::ResolvedViewBits`: the occlusion maps', then `lodPhases`).
- **The view engine.** A feature's work and epochs reproduce Core's own over the view's slot (`IndirectDraws.h`, "The view engine"):
  `ViewState`, `MainTargetFormats`, `SetViewTargets` (published for the scene lane), `PostViewInputs`, `SetViewDepthRange`,
  `ExchangeViewForwardCompatible`, `DrawPipelines::SetViewForwardTargets` (the view's forward targets, `PipelineCatalog::viewTargets`),
  `ResolveViewPipelines` (wanted slots or every slot; with the programs and waits counted on request),
  `DropViewPipelines`, `SetUpView`, `ImportViewTarget` (by its target import), `TakeViewInputs` (`DepthThisFrame`,
  `DepthThisFrameTargetAfter`: the same commit, the target imported after; `ColourThisFrame`), `SubmitViewEpoch`
  (the revision's recording and shape, the payloads held, the faces committed, a view with frame constants of its own its frame
  record and rows too, from this frame's sources, Core/Render/Resources/FrameRecords.h: `Submitted`, `NoRevision`, `NoOwners`, `Failed`, which the
  feature maps onto its own skip causes and log lines), `ViewCovered`, `ViewDrawable`. A trees view's draw families per face are the view engine's
  (`ResolveViewFaces`, `DecideViewFaces`, per family, a no-op unless the view has trees; the rows `SubmitViewEpoch` commits), drawn by each
  family's faces while the family is on (`TreeInstances`: Features/TreeLod's, under `ObjectClass::TreeLod`); a view feature reaches them
  through these calls, never a LOD feature's headers.
- **View roots.** A covered view's owned roots (`ViewLodRootsOwned`, `Core/Render/Views/ViewRoots.cpp`, once per plain render) are the OR of

  under `Views().rootBits`.
- **Withholding.** `PassCapture` keeps each view's renderers and coverage (before the first decision, its `coveredInitially`). An

  `SetViewRendering` marks its render for the observers.
- **Hooks and shell state.** A view feature's engine hooks are its own (from its install, or its early hooks when Core's engine side and
  observers must find them in place); they read `Core/Engine/ShellState.h` (`Running`, `Passes`). The shell's `Main_RenderDepth`
  world-drawn point runs `FrameDriver::DepthCommitted` (the depth commit, then the `DepthCommitted` work).
- **Reports.** A view's lines go at `ReportPoint::AsyncWorkViews` (after the visibility lines, before the forward epoch's) or
  `AsyncWork` (after it); a CategoryRoot view's scene-side lines at `SceneCoordinatorSet` (the coordinator's set lines).

## The shadow-view contract

Every caster view (sun, spot, point, focus) is drawn by one shadow engine: one execution (`ExecuteShadowFrame`), one `ShadowPayload`,
one set of resources and index pool, one latch block and one key group (`kKeyShadow`); the occlusion epoch (`ExecuteOcclusion`) draws
from the same commit. Casters are keyed by the engine's render mode, not by source, so the sources own no phase or view bit. The
features take the parts that are theirs through `Api/ShadowViews.h` (`RegisterOcclusionMap`, `RegisterShadowSource`,
`RegisterShadowExclusion`) and `Api/SunVolume.h` (`RegisterSunVolume`), with their Core companions `Core/Extensions/ShadowViews.h` and
`Core/Extensions/SunVolume.h`; the engine itself, its capability and captures, both epochs, the light candidates, the camera math
(`Core/Render/Shadow/ShadowCameras.h`) and the views list's input (the selection's `LightSlots`, `Core/Handoff/ShadowViews.h`), the
caster phases and modes, and the shadows' toggles stay Core's. The exclusions' type and slots are the exclusion contribution's
(Features/Shadows/Local's `SunExclusion.h`), opaque to Core. The camera boards are the sources' features' (below). The light selection is Features/LocalLights' (below), and its
volumes reach Core on the light volumes contract (`Api/LightVolumes.h`).

- **The occlusion maps.** `OcclusionMapContribution`: the map (Core's slot order, `kOcclusionSky`, `kOcclusionPrecipitation`: its mode,
  view slot, depth target and technique column), its toggle and `available` flag, its `ViewBits` (the feature's own), its occluder rule
  (`technique`: the scene work, per walked entry while the map is on, for a non-LOD object with a Lighting property, pure; resolved once
  at install, called at the walk, the classification's one call per entry per map), its size test (`minRadius`, `kCullMinRadius` in the
  map's latch), its target (`EngineMask`, or `ImportedTexture` with
  `importTarget`, called once as the capability sets the maps up, in Core's import order: the precipitation mask, then the sky map), its
  labels (the view-mask parity's list, the report lines', the imported target's) and its optional `referenceDue` (the engine's
  reference frame for the map's parity, asked by the shell's `OcclusionReferenceFrame`), its `camera` (the shell's `OcclusionView`) and
  `ownsAccumulator` (the shell's 0x1C capture, the maps asked in slot order until one owns the accumulator). `Extensions::OcclusionOn` is whether DCLF
  draws a map (taken, available, its toggle on); a map's phase and view bit reach the set decisions, the classification, the builds'
  masks, both epochs and the reports through its entry.
- **The shadow sources.** `ShadowSourceContribution`: the source (`Sun`, `Spot`, `Point`, `Focus`), its `camera` (required: render
  thread, an `Api::ShadowSourceCamera` per view the capture takes and per kept light's descriptor the light volumes' sample reads,
  `Extensions::SourceCamera`: DCLF's camera for the view's light, descriptor and scene frame, null when none, and a focus view's target
  node), for a spot or point source
  `lightKept`, called at the end of the light selection for each kept light of its kind, in the selection's order, and for the sun

## The schedule

Every pass DCLF adds to the graph is an `Api::PassDef` (`Api/Passes.h`): a key, the graph pass's name, its kind and queue, and either a
`make` (render thread, at the graph's build: the pass, or null when its conditions are unmet) or an `emit`.
- **Keys** name their owner by prefix: `core.*` (the main view's culling and copies), `view.*` (Core's, registered
  from `Core/Render/Passes/CorePasses.cpp` before the features install; the view passes' table stays beside their classes, in
  `Epochs/ViewEpochRecord.cpp`), and the features' own: `main-view.*` (Features/MainView: the main view's
  depth draws in both phases and its colour draws), `shadows.*` (Features/Shadows/Engine: the shadow epoch's and, as `shadows.sky.*`,
  the occlusion epoch's latched copies, culling, views' draws, index pool copies and culling counters), `forward.*` (the forward epoch's draws and refraction normals), `tree-wind.*`, `fades.*`,
  `texture-transforms.*`, `tree-lod.*` (its cull, retest, counts and a trees view's faces' cull), `gpu-occlusion.hzb` (the depth
  pyramid's producer). A feature registers its passes with `InstallContext::RegisterPass`, from its own folder. A view pass's name
  says `{view}`, which becomes the view's prefix.
- **A pass's state.** A PassDef with a `make` may have a `setup` (render thread, once, where the scene's GPU tables are made, in
  registration order, handed `Api::PassSetup`: the device and the scene's tables). Its result is the pass's state, held with the
  scene's tables (`SceneBuffers::passStates`, by pass) and handed to `make` (`PassContext::State`); while it is null the pass is not
  added. A pass with a setup is scheduled only in a Main or View epoch.
- **The latch word.** One PassDef may have a `latchWord`: the depth commit's `BuildDrawsLatch` stage word, which its shader reads
  (`texture-transforms.apply`'s pool rows). A second fails the install (grow the latch first), as does scheduling it anywhere but in
  `main.depth` before `core.z.build-draws`.
- **Phase 2.** `PassContext::PhaseTwo` says whether the main resources have the depth pyramid; the depth epoch's phase 2 block (the
  pyramid's pass, the retest build, `tree-lod.cull-phase2`, the rescues' depth draw) returns null without it.
- **Anchors** exist only for diagnostics: `diag.*` are PassDefs with an `emit`, which adds the `MainGraphPasses` observers' passes at
  that point, any number of them.
- **The table** (`Schedule/Frame.cpp`, `Api/Epochs.h`) defines every epoch and the engine point it is submitted at; nothing else does.
  Only the shell includes it, handing it to `Extensions::InstallFeatures`; Core never includes `Schedule/`. It reads as the whole
  frame: its triggers first, in the frame's order, then the epochs. An `Api::EpochDef` holds:
  - its `id` and `label` (the reports' name), its `trigger` (a `TriggerDef` id, below) and its `RenderGraphRuntime::Segment`;
  - the shape its passes are made from and record against (`shape`, `Api::EpochShape`: the main, shadow or a view's extension's
    resources) and its index there (`shapeIndex`: `Api::MainShape` depth or colour; shadow 0, occlusion 1; the `Api::EngineView`);
  - `sharesWith`, the id of an earlier epoch whose shape it records against instead of its own (`forward`: `main.colour`;
    `fp.colour`: `fp.depth`);
  - `gate`, an `Api::ObjectClass` (none: `Count`): while it is off the shared shape is not taken and the frame's claims don't need the
    epoch; `claims`, whether the frame's claims need its recordings (`main.depth`, `main.colour`, and `forward` under its gate);
  - `revision`, whether it is revision-driven (every DCLF epoch is); and its pass keys in order, Core's and the features' side by side.
- **The orders.** The rows' order is the scene revisions' slot order and the reports' order: an epoch is its row's index in Core
  (`Core/Render/Revision/Epochs.h`: `EpochCount`, `EpochTraitsOf`, `EpochOfShape`, `EpochById`, `ViewEpochsOf`; the fixed arrays hold
  `kMaxEpochs`). The order a frame runs them is `frameOrder`, the host's async ticket loop's `asyncOrder` (its revision-driven epochs
  are the ones with `revision`), both by id and naming every epoch once, the `ForeignEpoch`s too (Light Limit Fix's `light-culling`:
  live, never revision-driven). The shell hands them to `RenderGraphRuntime::ConfigureFrame` (`Extensions::ScheduledFrameOrders`) before
  the runtime initializes; without DCLF the runtime keeps its built-in orders.
- **Triggers.** A trigger (`Api::TriggerDef{id, owner, where}`, `FrameSchedule::triggers`) is an engine point epochs are submitted at:
  `owner` names whose hook it is (`Core`, `Features/Forward`, ...), `where` the engine point and the hook. The table's, in the frame's
  order: `shadow-maps.after` (Features/Shadows/Engine: Deferred's `Main_RenderShadowMaps` returned, its shadow epochs handler called
  from FrameDriver; `shadow`), `depth.committed` (Core: the shell's
  `Main_RenderDepth_WorldDrawn`; `main.depth`, and `reflection` from the views' work there), `fp.depth-draw` (Features/FirstPerson:
  RenderDepth's first-person draw; `fp.depth`), `occlusion.draw` (Features/Shadows/Engine: Skylighting's `DrawOcclusion`, its handler called from FrameDriver; `occlusion`), `opaque.after`
  (Features/MainView: the opaque batches done, `Main_RenderWorld_BlendedDecals`, its primary view handler called from FrameDriver;
  `main.colour`), `blended.draw` (Features/Forward: the main pass's
  blended draw; `forward`), `fp.colour-render` (Features/FirstPerson: `Main::RenderFirstPersonView`'s accumulator render; `fp.colour`).
  - The owners keep their hooks (they take the engine's arguments and return values). A hook marks its trigger active on the render
    thread for the duration of its DCLF work: Core's FrameDriver points directly (`Draws::CoreTriggerOf`), a feature with the id it
    found at install (`InstallContext::FindTrigger("blended.draw")`; an unknown id fails the install) and an
    `Extensions::TriggerScope scope(id)` around the hook's DCLF call. The active trigger is one render-thread integer; scopes nest
    (each restores the one it found), with no allocation and no lock.
  - The check: `IndirectDraws::Impl::SubmitRevisionRecording` compares the active trigger with its epoch's, one integer compare,
    always on. A mismatch is counted and logged once per epoch: `[DCLF] the {epoch} epoch was submitted outside its trigger
    {trigger} (active: {active})`.
  - The resolve fails the install for a trigger id missing or duplicated, an epoch's trigger the table has not, a trigger no epoch
    names, or one of Core's (`Draws::CoreTrigger`) missing.
- **A new epoch** is a CS segment (`RenderGraphRuntime::Segment`), a row in the table (with its place in `frameOrder` and `asyncOrder`),
  its trigger and its passes. Its trigger is an existing `TriggerDef` when it is submitted at that point, or a new one: a row in
  `kTriggers` at its place in the frame, and its owner's hook marking it (a feature's: `FindTrigger` at install and a `TriggerScope`
  around the submitting call). Its shape must be one Core records (a main or shadow shape, or a view's); a new kind of shape is Core's work first.
- **The executor** (`Core/Render/Epochs/ScheduleExecutor`) keeps every registered PassDef (a missing or duplicate key, neither or both
  of make and emit, or an anchor with a setup or latch word fails the install), resolves the table once at the end of
  `InstallFeatures` (a key nobody registered fails it, naming the epoch; so do the setup and latch word rules above, an epoch id unknown
  or duplicated, a segment used twice, a `sharesWith` naming no earlier epoch recording that shape itself, a shape of Core's no epoch
  records, an order not naming every epoch once, more epochs than `kMaxEpochs`, and the trigger rules above), resolves the trigger ids
  to their rows (`EpochTrigger`, `TriggerName`, `CoreTriggerOf`), runs the setups
  (`SetUpPassStates`, from `EnsureSceneBuffers`), gives the depth commit its latch word (`PassLatchWord`), and adds an extension's
  epochs' passes when its `GatherStructuralPasses` asks (`GatherScheduled`), epoch by epoch in table order. ORG orders the epochs;
  within an epoch the passes keep the table's order. Each extension registers its own resources in `PrepareForBuild`.
- Rule 6 below keeps it the one way in: nothing else adds a pass.

## The rules

`tools/dclf-layout-check.py` checks these.

1. **Only the shell tests `CS_HAS_DCLF`.**
   - CMake defines it when the render graph and ORGModuleServices are present, and otherwise leaves the DCLF tree out of
     the build.
   - No file in the tree tests a dependency macro (`CS_HAS_DCLF`, `CS_HAS_RENDER_GRAPH`, `CS_HAS_ORG_MODULE_SERVICES`,
     `ORG_MODULE_SERVICES_HAS_DXC`): the tree is not built without them (`cmake/RenderGraph.cmake`).
2. **The rest of CS reaches DCLF only through the shell.** No file outside the tree includes a header inside it.
3. **Includes point one way.**
   - `Api/` includes `Api/`.
   - `Core/` includes `Api/` and `Core/`.
   - A feature includes `Api/`, `Core/`, its own folder, and the features it declares as dependencies.
   - An integration includes `Api/` and `Core/`.
   - The dependencies are the check's `DEPENDS` (Shadows/Sun: Shadows/Engine, Shadows/Local; Shadows/Local: Shadows/Engine;
     OcclusionMaps: Shadows/Engine; LocalLights: Portals; FirstPerson: Actors, Skins; Effects: Skins; Actors: Shadows/Sun, Shadows/Local).
   - `Diagnostics/` may be included from anywhere. Production code reaches it only through its observer contract (`Hooks.h`,
     `Observation`, `Policy`), which the parity rework redefines ("Not yet in place").
4. **A dependency installs first.** Every feature `DEPENDS` names is listed in `Features/FeatureList.cpp` before the feature that
   depends on it, so its registrations (toggles, classes, report lines) run first.
5. **The top level is closed.** Every file is in `Api/`, `Core/`, `Features/`, `Integrations/`, `Diagnostics/` or `Schedule/`,
   none at the tree's root, and `Core/` holds only the subfolders in the tree above (`TOP_LEVEL`, `CORE_SUBFOLDERS`). A new layer
   folder doesn't grow back.
6. **Passes reach the graph through the schedule's executor alone.**
   - Under the tree, `AddPass(` and `.Epoch(` appear only in `Core/Render/Epochs/ScheduleExecutor.cpp` (the gather and
     `PassOut::Add`), in `Core/Render/Passes/PassHelpers.h` (AddPass's definition) and in `Diagnostics/`, whose `MainGraphPasses`
     observers append finished descs at the `diag.*` anchors ("Remaining architectural flaws").
   - `host->AddExtension` appears only in `Core/Render/Resources/Resources.cpp`.
   - `Schedule/` includes only `Api/` (and CS's `RenderGraph/RenderGraphRuntime.h`); nothing under the tree includes `Schedule/`:
     only the shell does.
7. **Complexity may only shrink.** The functions over the thresholds (120 lines or cyclomatic complexity 40) are counted
   against a baseline, which each split lowers (`--update`). A function not in the baseline may not cross them. `EXEMPT`
   names the ones not counted, each with its reason (a data table, a flat verdict chain a split would only fragment).
8. **Features don't reach into Core's renderer.**
   - No file under `Features/` or `Integrations/` (their own `Diagnostics/` folders included) includes IndirectDraws'
     implementation internals: `Core/Render/Internal.h`, `Core/Render/Impl.h`, `Core/Render/Impl/` or
     `Core/Render/Passes/PassesInternal.h`.
   - A feature includes the self-contained Core headers it uses instead: `Main/Resources.h`, `Revision/Shapes.h`,
     `Resources/Helpers.h`, `Resources/SceneBuffers.h`, `Payload/Versioned.h`, `Payload/Uploads.h`, `Payload/MainRows.h`,
     `Epochs/ViewEpoch.h` and so on. The pass authoring helpers (`Draws::Register`, `Draws::RecordDispatch`) are
     `Core/Extensions/PassContext.h`'s.
   - A feature or integration names no `RenderGraphRuntime::Segment::` value. A pass reads its epoch from the `Api::PassContext`
     it was made with (`segment`, captured by its make), so the schedule alone decides where it runs. Only `Schedule/` and Core
     may name one.
   - `Internal.h` stays Core's umbrella. The top-level `Diagnostics/` is exempt (its `Draws/DrawsView.h` names the
     implementation for the observers).

## Remaining architectural flaws

What Core keeps that a feature alone uses, and why. The first is the largest.
- **BuildDrawsCS composes every feature's cull logic in one Core shader.** One compute program (`kBuildDrawsShader`,
  `features/Drawcall Limit Fix/Shaders/DrawcallLimitFix/BuildDrawsCS.hlsl`) runs once per view and phase and holds, switched by latch
  words and bindings rather than by features registering code:
  - Features/Portals' room programs (`PortalPrograms.hlsli`, phase 1 and FadeStateCS);
  - Features/Fades' root fading, LOD partitions and seed state (`RootFading`, `LodPartitions`, `SeedState`; the fade test reads the
    latch's `fadeEye`/`treeHeight`, written from Fades' `latchGlobals`);
  - LocalLights' local shadow mask (object-word bits 26-29, `LocalShadowMask`), and Shadows/Sun's cascade test and sun miss
    (`InSunCascades`, `kObjectSunMiss`, `OutsideSunEntry`);
  - the shadow views' branches (`CastersOnly`, `VolumetricOnly`, `SunEntry`, `MinRadius`, `FadeOnVisible`, `FocusRoot`);
  - the decal ordinals and terrain-group ranges (Decals, Terrain Blending), the forward staging and refraction ranges (Forward), the
    first-person forward branch, the HZB test TreeLod's cull shares (`HzbTest.hlsli`), and the one feature stage word
    (TextureTransforms' latch word).

  So a feature's GPU behaviour in the cull is Core's code: adding or changing one edits Core's shader and its latch layout
  (`BuildDrawsLatch`, `GpuLayouts.h`), and the latch has room for one stage word. It stays because it is one dispatch per view and phase:
  giving a feature its own cull pass would walk the scene list and read the visibility words again (extra GPU work), which is
  ruled out. A fix keeps the single dispatch and moves the code: each feature contributes an `.hlsli` of stage functions plus a range of
  latch words, and the program is generated from the registered stages at shader-compile time (an include list and a stage table in
  feature order), so the features own their cull code and Core owns only the walk, the visibility words and the stage calls.
- **Refraction's pipeline** (`DrawPipelines::RequestRefraction`, `SetRefractionInputs`, the catalog's refraction entry, `kRefractionTechnique`;
  `Core/Gpu/Pipelines/ForwardPipelines.cpp`) is Features/Forward's alone, but stays Core's: no pipeline contract fits it. A program family
  (`Api::ProgramFamilyContribution`) is a material port's keys built into the main pipeline set at a fixed family slot, its key bits read
  per object; refraction is one dedicated pipeline (the Utility shader's RENDER_NORMAL, with its own layout and draw signature, built for
  the imported normals' format and the engine's write mask) that the pipeline lane builds and publishes into the frame's indirect state
  (`PassFrame::indirect.refraction`, `refractionLayout`, `refractionDrawSignature`, `refractionFormat`), part of every revision's shape. A
  contract for it would be a feature pipeline the lane builds from feature inputs and publishes into the shape: new machinery for one
  pipeline. The feature drives it (`RequestRefraction`, `SetRefractionInputs`, from its `prepare`).
- **The main pass's preprocess state lists** (`Resources::preprocessMain`, `Main/Resources.h`) are MainOpaquePass's alone, but stay with
  Core's main resources: Core makes them with the rest (`Impl::CreateMainBuffers`, at the first colour frame and each target change, one per
  frame slot), and no contract gives a feature state of its own made with the main resources. Making them in the pass's make would make them
  at every graph build, not with the resources.
- **The foliage record** (`Resources::foliage`, `FoliageRecord`; `Policy::RecordFoliagePixels`) is Diagnostics' (its compare pass and
  parity, `Diagnostics/Draws/Foliage.cpp`), but Core makes it with the main resources (`CreateFoliageRecord`), the colour commit writes its
  words (`Payload/Uploads.cpp`), the shape's latched layout and the main extension's registration name it, and MainOpaquePass declares it:
  entangled with Core's main resources and commit, so it stays.
- **The refraction range in the shared shader interface.** The refraction words of `GpuLayouts.h` (`kCountRefractionWord`, the range's
  slots after the forward halves, `RefractionSlot`) and `LightingConstants.h` are BuildDrawsCS's: it classifies and writes the refraction
  range with the other ranges, so they stay Core's with it (the BuildDrawsCS flaw: one shader holds every feature's range).
- **The sun and light candidates** (`Core/Scene/Coordinator/SunCandidates.cpp`, `State/Candidates.h`'s `CoordinatorCandidates`,
  `FrameView::GetSunCandidates`/`GetLightCandidates`, and the light-entry rule, `Coordinator::LightEntryOf` and the attach's listing in
  `Classification.cpp`) are scene-side shadow data, like the shadow columns, but stay Core's: `Api::CoordinatorComponent` cannot carry
  them without per-object callbacks or a new kind of contract. They are fed per object, inside the coordinator's own paths: the attach
  lists each geometry under its entry and light roots (`rootDependents`, `lightDependents`) and marks them dirty (`MarkListedRootDirty`,
  `MarkLightEntryDirty`) on the classification, the walk's write and the unlist, with the entry's verdicts (`PrimaryEntryAllows`, its
  slot and candidate reason) folded into each candidate's signature; a component sees only slots and events through its own hooks, so
  every one of those sites would become a per-object callback. And their product is no component's private state: the candidates'
  `EntrySpace` snapshots are read by Core itself, by identity, at a dozen places (the walk and its events, `SceneSet`'s publication,
  `Model/Publication.h`, the revision participants' ahead build and coverage, the snapshot, the visibility readback, the main build, the
  primary cull's cut and scene-list filter, the shadow inputs), so a component owning them would need a contract by which a feature
  hands Core an index space it then plans, filters and translates against: new machinery, not the existing component contract. The
  exclusions over them are Features/Shadows/Local's (opaque to Core, read through `Api::ShadowListExclusion`).
- **The shadow engine's scene side and commits.** Features/Shadows/Engine owns the shadow and occlusion epochs' passes, their frame points
  and triggers; Core keeps the rest of the shadow engine:
  - the scene side (`Core/Render/Shadow/ShadowEngine`, its revision participant: the requirements, the latch, the shapes and variants, the
    shadow payload; the shadow table columns; the walk's caster verdicts; PassCapture's withholding; the views list the capture builds,
    `Handoff/ShadowViews`, listed by Core in the engine's shadow-light selection: begun before `CalculateAndDrawShadowCasterLights`, each
    light added at its keep, rebuilt from DCLF's selection when it returns, `Draws::ListShadowViews`): everything a frame's set and revision decide
    before an epoch runs, read by Core's own producer, coverage and capture;
  - the captures (`IndirectDraws::CaptureShadowView`, `CaptureOcclusion`, at the shell's FinishAccumulating hook): the scene side's input;
  - the shadow pipelines (`DrawPipelines`' shadow set, published into the shapes like refraction's: see above);
  - the shadow extension and its resources' registration (`Passes/Shadow.cpp`, added from `Resources.cpp`, rule 6), as the main and view
    extensions';
  - the epochs' commits (`IndirectDraws::ExecuteShadowFrame`, `ExecuteOcclusion`, `Shadow/ShadowEpochs.cpp`), which the feature's handlers
    call. Like Features/Forward's shared-epoch submission, they hold nothing feature-specific: every step writes Core's private state
    (`failed`, `stats`, `shadowStats`, the revision's latch clamps and misses, the shadow engine's committed payload and execution owner),
    every early return counts into those counters, and the decision to submit is the toggles' and the revision's, which they read
    themselves. So the bodies stay Core's whole, each executed in its epoch's segment (`EpochTraitsOf(epoch).segment`, no literal), and
    the feature holds the calling and the triggers.
- **Diagnostics' passes reach the graph through anchors.** The `diag.*` keys are the only anchors: Diagnostics' `MainGraphPasses`
  observers append finished descs (cull counters, the foliage compare) at three points, exempt from rule 6 ("Not yet in place").
- **Kept in Core on purpose (not flaws, recorded so they are not moved by accident):**
  - **Billboard rows** (`Core/Gpu/PlacementRows/BillboardRow.h`): sampled for every moving object whatever the toggle, read per slot
    by three parities, and laid out as Effect.hlsl's frozen `DCLFBillboardWorld` decode; the header gives the full reasoning.
    Features/Billboards owns the switches, toggle, parent contributions and the CPU twin of the turn.
  - **Skin partitions** (`Core/Engine/SkinPartitions.h`, the `skinPartitions`/`skinLodPartitions` columns): the engine's rule for which
    partitions a skinned geometry draws, woven through the walk's geometry slots, the main build and the index pool's sizing, like the
    LOD rows. Moving them means generalising `Api::EntryRanges` to partition chains on the walk's per-geometry path.
  - **The ProjectedUv toggle and the particle capture fields** (`Core/Settings/Toggles`, `LightingDescriptors.cpp`;
    `SceneCapture`'s particle fields, `PaletteItemClassOf`): each would need a contract it does not have (a property-flag rule with a
    reason other than LOD; a geometry-capture contribution, the geometry counterpart of `NodeCapture`) for a few dozen lines.
  - **The fixed-slot enums named after features** (`ObjectClass`, `EngineView`, `DrawFamily::TreeInstances`, `ProgramFamily::Effect`,
    `OcclusionMap`, `ShadowSource`, `MainRangeSlot`): Core's slot vocabulary, which features fill; adding a slot is a Core change by
    design.
